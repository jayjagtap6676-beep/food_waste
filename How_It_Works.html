How the database, backend and website work together

Food Waste Recovery & Redistribution. This page explains what each part does, which SQL object each page uses, what a user's click changes inside MySQL, and how to connect the MySQL file to the backend.

1. The big picture

The system has three layers. Each layer only talks to its neighbour: the browser never touches MySQL, and the backend never repeats the rules that MySQL already enforces.

Website (frontend)

  • 12 HTML pages in app/templates
  • Shows forms and tables
  • Sends what the user typed to the backend
  • Contains no SQL and no business rules
↔

Backend (Python Flask)

  • app.py login, register, dashboard, NGO verification
  • listings.py listings and requests
  • delivery.py deliveries, quality checks, reports
  • auth.py who may open which page
  • db.py the connection to MySQL
↔

Database (MySQL, food_waste_db)

  • 11 tables: the data
  • 7 views: ready-made reports
  • 9 triggers: the business rules
  • CHECK / UNIQUE / FOREIGN KEY: data integrity
Why this split matters: a rule placed in a trigger works for every way of reaching the data. Even a direct statement typed in Workbench cannot approve food that has expired or give an unverified NGO a request. If the same rule lived only in the website code, anything bypassing the website would bypass the rule too.

2. One click, end to end

Example: an NGO clicks Request on the Browse Food page.

StepWhereWhat happens
1BrowserThe form posts listing_id and quantity_kg to /ngo/request.
2Backend@login_required("NGO") checks the session. A donor or a logged-out visitor is sent away.
3Backendplace_request() runs INSERT INTO Collection_Request (listing_id, ngo_id, quantity_kg). The NGO id comes from the session, not from the form, so a user cannot request on behalf of another NGO.
4MySQLConstraints check the row (quantity > 0, foreign keys exist). Then trigger trg_request_bi fires: it looks up the NGO's verified status and the listing's status, expiry and remaining stock.
5MySQLThe trigger stores the row as Pending, or as Rejected if any rule fails. The insert and the trigger succeed or fail together.
6BackendReads the saved status back with SELECT request_status and chooses the message: "Request placed" or "Request rejected: ...".
7BrowserThe page reloads; the flash message appears and My Requests shows the new row.
Every value goes into the SQL through %s placeholders (cur.execute(sql, params)). The connector sends the values separately from the statement, which prevents SQL injection.

4. Views

A view is a saved SELECT. The backend asks for SELECT * FROM v_... instead of repeating a long join. The column names of each view are exactly what the matching page reads, so changing a view's column names breaks the page.

Views also keep data current without extra code: they use NOW(), so food that expires disappears from Browse Food the moment its time passes, even before the clean-up marks it Expired.

5. Triggers: where the rules live

Triggers are the rules. They run inside MySQL automatically, in the same moment as the INSERT or UPDATE that caused them. If something fails, the whole statement is undone, including everything its triggers did.

The failure chain

One quality check can change four tables with no extra Python code:

Volunteer saves a check at 12 C for milk
 -> trg_quality_bi      result = Fail
 -> trg_quality_ai      Delivery status = Failed
 -> trg_delivery_au     Volunteer = Available, Request = Cancelled
 -> trg_request_au      Food_Listing stock + 25 kg

6. Transactions (COMMIT and ROLLBACK)

A transaction groups several statements so they all happen or none do. Transaction control is used in the backend in these places:

ActionStatements groupedIf one fails
Register (app.py)INSERT login, INSERT profile, INSERT phone rowsROLLBACK: no half-registered user
Cancel listingReject its pending requests, then mark the listing CancelledROLLBACK: both or neither
Expiry clean-upReject pending requests on expired food, then mark listings ExpiredROLLBACK
Change delivery statusOne UPDATE; its triggers (volunteer, request, stock) run inside itROLLBACK of the whole chain

The helper in db.py:

def run_in_transaction(steps):
    conn = get_conn()
    try:
        cur = conn.cursor()
        conn.start_transaction()
        for sql, params in steps:
            cur.execute(sql, params)
        conn.commit()          # COMMIT: everything is saved
    except Exception:
        conn.rollback()        # ROLLBACK: everything is undone
        raise
    finally:
        conn.close()
A single statement such as Approve is already atomic: MySQL treats the UPDATE and every trigger it fires as one unit. Explicit transactions are needed when the website sends several statements for one action. Section 6 of the SQL file shows the same idea as plain SQL blocks for approving and assigning, registering a donor, and finishing a delivery. The website does not run those blocks; it uses the Python version above.

9. Connect the MySQL file to the backend

How the connection works

The SQL file only builds the database. The backend reaches it through app/db.py:

DB_CONFIG = {"host": "localhost", "user": "root",
             "password": DB_PASSWORD, "database": "food_waste_db"}

def get_conn():
    return mysql.connector.connect(**DB_CONFIG)
  • DB_PASSWORD is read from app/config_local.py (your own file, never shared).
  • The database name must be food_waste_db, which the SQL file creates.
  • Every helper (query, execute, run_in_transaction) opens a connection, runs the SQL and closes it.
  • The package that does the talking is mysql-connector-python, installed from requirements.txt.

Steps

  1. Install MySQL Server 8.0.16 or newer with MySQL Workbench, and Python 3.10 or newer (tick Add python.exe to PATH). Keep MySQL on port 3306 and remember the root password.
  2. Unzip food_waste_project.zip. You get sql/, app/, run_website.bat.
  3. Load the database. Open Workbench, connect to your local server, choose File > Open SQL Script, select sql/food_waste_full.sql, click the lightning icon. Run the whole file in one go (the triggers contain semicolons). It rebuilds food_waste_db each time.
  4. Check the load in Workbench:
    USE food_waste_db;
SHOW FULL TABLES;     -- 11 tables and 7 views
SHOW TRIGGERS;        -- 9 triggers
  5. Give the backend your password. Open app/config_local.py and write:
    DB_PASSWORD = "your_mysql_password"
    If your MySQL user is not root or the port is not 3306, edit DB_CONFIG in app/db.py (for example add "port": 3307).
  6. Install the Python packages. Open Command Prompt in the app folder:
    pip install -r requirements.txt
  7. Test the link before starting the site. In the same folder:
    python -c "from db import query; print(query('SELECT COUNT(*) AS found FROM information_schema.tables WHERE table_schema=%s', ('food_waste_db',)))"
    Expected output: [{'found': 18}] (11 tables + 7 views). An error here means the connection or the SQL load is wrong; see the table below.
  8. Start the website:
    python app.py
    (or double-click run_website.bat in the unzipped folder, which installs the packages and starts the site). Open http://localhost:5000. Keep the black window open.
  9. Prove the website is changing MySQL. Log in as admin / admin123, register a new donor, then in Workbench run:
    SELECT donor_id, donor_name, user_id FROM Donor ORDER BY donor_id DESC LIMIT 1;
    The new donor appears. Approve a pending request on the website, then run SELECT listing_id, quantity_kg FROM Food_Listing;: the stock has dropped without the website sending any stock update, because the trigger did it.

10. Limits you should know about

  • Not yet run on a real MySQL server. The SQL was reviewed but never executed, and the website code was checked with a stand-in database. Your first run is the first real test.
  • Passwords are stored as plain text and compared directly in the login query. This was a project decision; real systems store hashes.
  • Roles are enforced by the website, not by MySQL users. The site uses one MySQL account (root) for everything.
  • Rejected rows stay in the table. A bad request is saved as Rejected instead of raising an error, which gives a history but means lists may need to filter them.
  • The status order and the passing-check requirement for deliveries are checked in Python, not by the database.
  • The Flask server is the development server (debug=True), suitable for a demo on one computer.
