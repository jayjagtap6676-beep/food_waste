Website demo script

Eighteen steps that use every role, every page, every trigger, the views and the transactions. Each step says what to click, what you should see, a query to prove it in MySQL, and a sentence you can say.

Before you start

Set up

  1. Load sql/food_waste_full.sql in Workbench (lightning icon, whole file). This resets everything.
  2. Start the website (python app.py) and open http://localhost:5000.
  3. Use two browser windows: a normal one for the Admin and a private window for everybody else, so you do not log out and in all the time. Log out before switching users inside a window.
  4. Open one Workbench tab, run USE food_waste_db;, and keep it beside the browser. Each step has a proof query: select it and press Ctrl + Enter.

Step 8: Cancelling a listing is one transaction NGODonor

Do
  1. As annadaan request 3 kg of Dal Rice (it is Pending).
  2. Log in as hotel_sunrise, open My Listings and click Cancel on Dal Rice.
  3. As annadaan open My Requests.
You should see
  • A message: Listing cancelled.
  • The Dal Rice request now shows Rejected.
Proof in Workbench
SELECT l.food_name, l.listing_status, r.request_status
FROM Food_Listing l JOIN Collection_Request r ON r.listing_id = l.listing_id
WHERE l.food_name = 'Dal Rice';
What this shows

The backend runs two UPDATEs inside one transaction (run_in_transaction): reject the pending requests, then cancel the listing. If either failed, both would be rolled back.

Say
"Two statements, one decision. COMMIT saves both, ROLLBACK would undo both."

Part 3: expiry clean-up, registration and rollback

Covers the expiry clean-up transaction and the registration transaction.

Step 15: The expiry clean-up NGOWorkbench

Do
  1. As annadaan request 4 kg of Assorted Bread Loaves (Pending).
  2. In Workbench make that listing expire.
  3. As annadaan reload Browse Food and then open My Requests.
You should see
  • The bread is gone from Browse Food.
  • The 4 kg request shows Rejected.
Proof in Workbench
UPDATE Food_Listing
SET expiry_on = DATE_SUB(NOW(), INTERVAL 1 MINUTE), pickup_deadline = DATE_SUB(NOW(), INTERVAL 5 MINUTE)
WHERE listing_id = 1;
-- reload Browse Food, then:
SELECT listing_id, listing_status FROM Food_Listing WHERE listing_id = 1;   -- Expired
SELECT request_id, request_status FROM Collection_Request ORDER BY request_id DESC LIMIT 1;   -- Rejected
What this shows

Browse Food, My Listings and Admin Requests all run the clean-up first: two UPDATEs in one transaction (expire_listings).

Say
"Time passing is handled for us. Every time a page opens, expired food is marked and its pending requests are rejected."

Step 16: Registration is all-or-nothing New userWorkbench

Do
  1. Log out. On the login page click Donor under "New here? Register as".
  2. Fill in: Username demo_cafe, Password demo123, any name, type Restaurant, a contact, an email, street, city, Pincode 4000 (only four digits), Phone 9000000001. Click Register.
  3. Run the first proof query. Then change the pincode to 400001 and register again.
  4. Log in as demo_cafe and open My Listings. Run the second proof query.
You should see
  • The first attempt fails with a red message about a check constraint.
  • The first query returns no row: the new login was rolled back.
  • The second attempt succeeds and the donor can log in.
Proof in Workbench
SELECT username FROM User_Account WHERE username = 'demo_cafe';
-- first attempt: no row. After the second attempt:
SELECT d.donor_name, u.username, p.phone
FROM Donor d JOIN User_Account u ON u.user_id = d.user_id
JOIN Donor_Phone p ON p.donor_id = d.donor_id
WHERE u.username = 'demo_cafe';
What this shows

Registration inserts the login, the donor and the phone numbers in one transaction. The login was created first, the donor insert hit the pincode CHECK, and ROLLBACK removed the login too.

Say
"Without the transaction we would be left with a login that has no donor behind it."

Step 18: No kilogram lost Workbench

Do
  1. Run the reconciliation query.
You should see
  • For the five original listings, remaining plus allocated equals 50, 40, 60, 80 and 10. The two new listings (Dal Rice 10 kg, Old Bread 5 kg) show as themselves.
Proof in Workbench
SELECT l.listing_id, l.food_name, l.quantity_kg AS remaining,
       COALESCE(SUM(r.quantity_kg), 0) AS allocated,
       l.quantity_kg + COALESCE(SUM(r.quantity_kg), 0) AS original_total
FROM Food_Listing l
LEFT JOIN Collection_Request r ON r.listing_id = l.listing_id AND r.request_status IN ('Approved','Completed')
GROUP BY l.listing_id, l.food_name, l.quantity_kg;
What this shows

The stock triggers kept the numbers consistent through approval, a failure and a return.

Say
"After approvals, a failed delivery and returns, every kilogram is still accounted for."
